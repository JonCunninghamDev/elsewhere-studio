# Elsewhere Studio

Elsewhere Studio is a generative media studio for creating ambient visual scenes that feel alive without demanding attention. The core visual idea is **micro-animation**: start with a strong still scene, then add restrained, deterministic motion such as camera drift, atmospheric movement, subtle light variation, steam, particles, or distant activity.

The long-term service is intended to take a scene from concept through animation, quality gates, rendering, and eventually publishing. The first product milestone deliberately proves only the creative/rendering loop.

## Why this exists

Most fully generated video pipelines ask a model to recreate the whole frame continuously. That is expensive and can introduce warping, visual discontinuity, and obvious AI artifacts. Elsewhere Studio instead treats a still image as the stable source of truth and adds controlled motion around it.

The working design principle is:

> Movement should usually be felt before it is noticed.

This makes the system particularly suitable for ambient, focus, sleep, display, and background media.

## Current state

**Status:** MVP / Studio v0.1 in development.

The current vertical slice provides:

- a TypeScript + React + Remotion project;
- a versioned, Zod-validated scene manifest;
- a sample scene: `The Observatory Above the Clouds`;
- Remotion Studio preview with editable Zod-backed props;
- micro-animation parameters for camera push, horizontal drift, atmosphere, and light flicker;
- a 30-second H.264 render command;
- repository-policy tests, scene-schema tests, type checking, and CI;
- render output excluded from Git.

Not implemented yet:

- audio layers;
- loop-continuity scoring;
- long-duration 30-minute / multi-hour output;
- 9:16 derivatives;
- AI scene generation;
- automated content novelty checks;
- thumbnails and metadata;
- YouTube upload, scheduling, or publishing;
- a bespoke Elsewhere Studio web UI;
- Blender/3D rendering.

## Architecture

### Current pipeline

```text
scene.json
    |
    v
Zod validation + TypeScript type inference
    |
    v
Remotion composition
    |
    +--> Remotion Studio preview / prop editing
    |
    v
deterministic micro-animation
    |
    v
Remotion render
    |
    v
renders/*.mp4
```

### Why these choices

**Manifest-first scenes**

Each scene is described by a small versioned JSON manifest instead of hard-coding creative parameters throughout React components. That gives automation a stable contract and gives future scene generators, quality gates, and publishing jobs a common object to work with.

**Zod as runtime boundary**

TypeScript protects code written by developers, but future scene manifests may be generated by software or AI. Zod validates those inputs at runtime while also providing the TypeScript type. The same schema is exposed to Remotion Studio so the scene properties can be edited interactively.

**Remotion before a custom editor**

Remotion already provides a capable Studio and programmatic render pipeline. Building a custom web editor before we know which creative controls matter would add product complexity too early. Studio v0.1 uses Remotion directly; a bespoke UI comes later only if the workflow proves it is useful.

**Deterministic micro-animation**

Animation is calculated from the current frame and explicit manifest values. We avoid runtime randomness. A given scene manifest should produce the same motion every render, which is important for debugging, quality comparison, and automation.

**Still image as visual source of truth**

The MVP animates a single stable source image and synthetic overlays instead of regenerating video frames. This should reduce visual warping and make seamless or near-seamless ambient motion easier to control.

**Local render artifacts**

Rendered media lives in `renders/` and is ignored by Git. Source code, manifests, and lightweight source assets belong in version control; large generated videos do not.

**Node/TypeScript first, Python available**

The rendering product is currently Node/TypeScript because Remotion is React-based. The repository also retains the Engineering Platform's Python capability for future media analysis, QC, ML-assisted scoring, or automation where Python is the better tool.

**Engineering Platform consumer**

Elsewhere Studio consumes `JonCunninghamDev/engineering-platform` release `v1.0.0`, pinned to commit:

`b107c9306161b395cbcaffebb55e47850b999560`

The shared platform governs reusable engineering mechanics and CI. Product architecture, render behavior, visual acceptance, media QC, and publishing decisions remain local to this repository.

## Development environment

### Requirements

- Node.js 22 or newer
- npm
- Git

Remotion may download or use a compatible browser for rendering depending on your local environment.

### Setup

Clone the repository and use the integration branch:

```bash
git clone https://github.com/JonCunninghamDev/elsewhere-studio.git
cd elsewhere-studio
git checkout develop
npm install
```

Dependencies are currently pinned to exact versions in `package.json`. A committed npm lockfile will be added once dependency installation is performed from a normal networked development workstation; until then, use `npm install`, not `npm ci`.

### Preview the studio

```bash
npm run studio
```

Open the local URL printed by Remotion. Select `MicroScene`. The composition's Zod schema exposes the scene properties in Remotion Studio, including the motion parameters.

### Render the sample scene

```bash
npm run render:sample
```

Output:

```text
renders/observatory-above-clouds.mp4
```

The sample is 1920x1080, 30 fps, and 30 seconds long.

### Validation commands

```bash
npm test
npm run typecheck
npm run build
```

`npm test` includes both repository-policy validation and scene-manifest tests.

## Scene manifest

The current sample lives at:

```text
src/scenes/observatory-above-clouds/scene.json
```

Example:

```json
{
  "schemaVersion": 1,
  "id": "observatory-above-clouds",
  "title": "The Observatory Above the Clouds",
  "durationSeconds": 30,
  "fps": 30,
  "width": 1920,
  "height": 1080,
  "source": "scenes/observatory-above-clouds.svg",
  "motion": {
    "cameraPush": 0.018,
    "horizontalDrift": -0.008,
    "atmosphere": 0.28,
    "lightFlicker": 0.035
  }
}
```

The schema intentionally bounds motion values. Elsewhere Studio should make it difficult to accidentally turn subtle ambient movement into obvious camera animation.

## Delivery workflow

Elsewhere Studio has exactly two long-lived branches:

- `develop` is the default and integration branch.
- `main` is production/released state.

Temporary work branches are created from current `develop`:

```text
develop
   |
   +--> feature/*
   +--> fix/*
   +--> agent/*
            |
            v
        PR + CI
            |
            v
         develop
```

Production promotion is separate:

```text
develop -> PR + full CI -> main
```

Both `develop` and `main` are protected by GitHub rulesets. PRs require:

- `Branch Route Policy`
- `platform-ci / Platform Consumer CI`

CI also enforces that ordinary temporary branches target `develop` and that only `develop` may target `main`.

See `AGENTS.md`, `engineering-policy.json`, and `docs/branching.md` for the authoritative engineering rules.

## Roadmap

The expected progression after the MVP is:

1. validate the first scene/render loop on real imagery;
2. add loop-continuity and technical media QC;
3. add modular ambient audio layers;
4. generate 30-minute and multi-hour outputs from one scene;
5. add 9:16 discovery derivatives;
6. add scene novelty/content quality gates;
7. add thumbnails and metadata generation;
8. upload privately to YouTube and verify the result;
9. add governed scheduling/publishing;
10. automate scene generation only after the downstream quality system is trustworthy.

The order is intentional: automate creative generation last, after we can reliably judge and publish what it produces.
